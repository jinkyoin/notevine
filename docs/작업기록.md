7일 차 결과
- **성능:**
  - 시작 1.6~2.1초, 검색 55~68ms.
  - 노트 1만 개 인덱싱은 처음 29.4초, 다시 열 때 5.9초. 개선 전에는 120.9초였다.
  - 1MB 노트에서 입력 지연 15ms. 개선 전에는 57ms였다.
  - 설치 파일 3.4~4.4MB.
- **사용성:** AI 테스터 3명이 실사용 테스트를 했다. 히스토리에서 여러 번의 수정이 첫 버전 하나로 합쳐지던 치명적 오류를 찾아 고쳤다(60초 쉬면 새 버전, 노트를 만든 버전은 따로 봉인). 업무일지를 찾기 어려웠던 점도 고쳤다.
- **CI:** 사용자가 통과를 확인했다.

보안 규칙 (계속 지킴)
- AI는 기본으로 꺼져 있다. 켜도 보낼 노트를 매번 보여 주고 확인을 받는다.
- CLI는 빈 임시 폴더에서 실행한다.
    - 웹 검색을 끄면 도구 없이 실행한다.
    - 웹 검색을 켜면 웹 검색과 페이지 읽기만 허용한다(Claude `WebSearch,WebFetch`, Codex `--search`).
- 노트 내용을 검색어에 넣지 말라고 AI에게 지시한다. 다만 질문과 관련된 표현이 검색에 쓰일 수 있다는 점을 확인 창에서 알린다.

결정 사항

## 5-3. AI 웹 검색 요청 (11-05)

요청: "'창발의 시대'란 도서를 검색하여 요약해줘"라고 하면 웹에서 찾아 요약하도록.

- 웹 검색을 분명히 요청한 질문·노트 작업은 노트를 보내지 않고 확인 창 없이 바로 검색한다 (`asksForWeb`, `src/ai.ts`). '웹 찾아보기' 설정이 꺼져 있어도 이 경우는 검색한다.
- 내 노트를 찾는 말(`노트에서`, `회의` 등)은 평소처럼 보낼 노트를 확인한다. 말로 판단하므로 틀릴 수 있다.
- 노트 작업 모드에서도 웹 검색을 쓴다. 제안은 여전히 사용자가 확인한 것만 적용한다.
- AI 지침을 바꿨다: 검색을 요청하거나 노트 밖의 정보를 물으면 노트가 있어도 웹을 검색한다.
- API 키·Ollama 연결은 웹 검색을 못하므로 이 요청에서 이유를 알려 주고 멈춘다.
- 보안 수정: 질문을 보낸 Enter가 곧바로 뜬 확인 창의 [보내기]까지 눌러 노트가 전송되는 경우가 시험 중 한 번 나타났다. 창이 열린 뒤 0.4초 안의 키보드 입력은 무시한다.
- 실측(Claude Code, `tests/e2e/ai-web-request.cjs`): 질문 54~63초, 출처 링크 포함, 보낸 노트 없음. 노트 작업 85초, 새 노트 제안 1건.

## 5-4. AI 입력 칸 통합 (11-05)

요청: 질문과 노트 작업 탭을 하나로. 질문할 때 무관한 노트가 보낼 목록에 오르는 이유 확인.

- 원인: 질문의 단어가 하나만 겹쳐도 후보가 되고, 최소 점수 없이 후보를 모두 미리 체크했다. 관련도(`relevant`)를 두어 단어 2개 이상 또는 제목에 있는 노트만 미리 체크한다. 단어가 하나뿐인 질문은 그 단어가 든 노트를 체크한다. 템플릿 폴더의 노트는 후보에서 뺀다.
- 탭을 없애고 `ask` 하나로 합쳤다. 답으로 끝낼지 변경을 제안할지는 AI가 정하고, 노트를 바꾸려면 항상 확인 창을 거친다 (사용자 결정).
- 말로 판단한다(`writeIntent`): "작성해 줘"는 열린 노트 끝에 덧붙이는 안, 열린 노트가 없으면 답과 저장·복사. "새 노트로 만들어 줘"는 새 노트 안.
- 템플릿: 템플릿 폴더에서 이름으로 찾아(`matchTemplate`) 확인 창에 표시하고 보낸다. 못 찾으면 있는 템플릿을 알리고 멈춘다. 템플릿은 고칠 수 없다.
- 웹만 요청하면 열린 노트 내용은 보내지 않고 제목만 보내며, AI에는 `열린노트.md`라는 별칭만 알려 준다. 폴더 이름은 새 노트 요청에서 확인을 거쳤을 때만 보낸다.
- "노트나 웹에서"처럼 함께 말하면 노트를 확인받고, 웹 검색은 켠다. 작성 결과를 저장할 때는 질문·답변 머리글 없이 글만 저장한다.

## 5-7. Google Drive·OneDrive 폴더 지원 (11-06)

드라이브 앱이 설치되고 로그인된 PC를 전제로 한다. 드라이브에 직접 접속(OAuth)하지 않고, 앱이 동기화하는 폴더를 안전하게 쓰게 했다 (FR-VLT-09).

| 항목 | 내용 |
| --- | --- |
| 저장소 이동 | 드라이브 폴더의 `history.db`·`index.db`·`workspace.json`을 `%LOCALAPPDATA%\net.notevine.app\vaults\<경로 해시>`에 둔다. 쓰는 중인 SQLite(WAL)를 동기화 앱이 올리면 깨질 수 있어서다. 기존 히스토리는 `VACUUM INTO`로 복사·검사한 뒤 옮기고 `.app/history-moved.db`로 남겨 다른 PC가 이어받는다. 드라이브에 다시 생긴 `history.db`는 합친다 |
| 드라이브 찾기 | OneDrive는 환경 변수, Google Drive는 고정 볼륨 이름 "Google Drive"와 프로필의 미러 폴더. 레지스트리에 마운트 경로가 없는 경우가 있어 볼륨 이름을 쓴다. 네트워크 드라이브는 멈출 수 있어 묻지 않는다 |
| 온라인 전용 | 색인·감시에서 읽지 않고 이름만 올린다(크기 -1로 표시해 나중에 받으면 다시 읽음). 노트를 열 때의 다운로드는 vault 잠금 밖에서 한다 |
| 저장 재시도 | 파일이 잠겨 있으면 저장·이동을 약 3초까지 다시 시도한다. 모든 노트 폴더에 적용 |
| 충돌본 | `이름 (1)`, `이름_conf(1)`, `[Conflict] 이름`(Google), `이름-PC이름`(OneDrive). 원본이 바로 옆에 있을 때만 충돌본으로 본다 |

결정 사항
- 저장소 폴더는 경로 해시로 정한다. 노트 폴더 안에 ID를 두면 복사한 폴더끼리 히스토리를 공유하게 된다.
- `workspace.json`도 함께 옮긴다. 열어 둔 탭은 PC별 정보이고 자주 바뀐다.

검증
- 단위 테스트(Rust 193개, 프런트엔드 244개)와 릴리스 빌드 실행 점검 21개. 실행 점검은 `OneDrive` 환경 변수를 임시 폴더로 돌린 가짜 드라이브로 했고, 온라인 전용은 `attrib +O`로 흉내 냈다.
- 실제 Google Drive 시험(11-06). Drive 앱의 메타데이터 DB 복사본과 Notevine의 색인·히스토리로 확인했다. Google Drive 커넥터는 인증 오류로 쓰지 못했다.
  - 저장소: Drive 폴더에 DB·임시 파일이 없다.
  - 업로드: Notevine에서 저장한 노트가 Drive 파일 ID를 받았고, 사용자가 웹 링크로 내용을 확인했다.
  - 웹에서 새 파일 올리기: PC에 내려받힌 뒤 7초 안에 앱을 다시 켜지 않고 색인·히스토리에 들어갔다. 수정 시각이 올리기 전 시각으로 남아 있어도 새 파일로 인식했다.
  - 웹에서 파일 교체: 내용이 다른 판은 4초 만에 히스토리(`external`)에 들어가 색인도 갱신됐다. 내용이 같은 판은 설계대로 건너뛰었다(내용이 같았다는 것은 사용자 확인).
